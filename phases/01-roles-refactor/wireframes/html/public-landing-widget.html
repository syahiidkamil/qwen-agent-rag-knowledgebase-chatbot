State C — chat_mode = internal, visitor IS signed in (any role)

Same as State A. The widget renders normally because the visitor has a valid Bearer token. Logged-in users (super_admin / admin / user) can chat from the public landing page just as they can from /workspace.

Other states

Loading landing_config

Widget area shows a low-fi skeleton block until config + auth state both resolve. ~150 ms ceiling on warm cache.

Mid-conversation flip to internal

The in-flight stream completes; next user message attempt receives 401; the widget UI replaces itself with State B's "Sign in to chat" block above the conversation history. History stays visible but greyed; no future sends possible.

API down

"Chat unavailable right now" — same as today.

Interactions

  • State B [Sign in] → navigate to /login; role-based redirect kicks in after success.
  • State A: existing chat flow, no change.
  • Minimize / maximize toggles: existing behavior, no change.

Notes

  • Landing page fetches GET /api/landing-config on mount and reads config.chat_mode (defaults to "public").
  • Backend chat endpoint independently enforces the gate: no Bearer + chat_mode internal → 401. FE check is UX-only; BE check is authoritative.
  • Single biggest visitor-facing change this phase (TC-01-006 covers it).
