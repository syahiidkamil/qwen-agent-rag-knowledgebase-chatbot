# TASK-01-002: Seed script for 3 roles + env vars

## Type
infra

## Milestone
Milestone 1 — Close security hole + role infrastructure

## Goal
A single command (`python -m app.scripts.seed_admin`) creates one user per role — super_admin, admin, user — idempotently, with passwords sourced from environment variables.

## Context
Today's seed script creates only `admin@airanext.id` with `role: "admin"` hardcoded into the source. The phase needs three seeded accounts (one per role) so testers, the implementer, and the client can exercise role-aware flows from day one. Passwords must come from env vars to remove hardcoded secrets from the script (the existing hardcoded `Qwenragadmin123!` stays only as a dev fallback when env is unset). This task is XS because the existing script's structure already supports the pattern; we just iterate over 3 specs instead of 1.

## Scope

### In scope
- Modify `repos/fast-api-backend/app/scripts/seed_admin.py` to seed three users:
  - `super.boss@airanext.id` with `role: "super_admin"`, password from `SEED_SUPER_PASSWORD`
  - `admin@airanext.id` with `role: "admin"`, password from `SEED_ADMIN_PASSWORD`
  - `cs.demo@airanext.id` with `role: "user"`, password from `SEED_USER_PASSWORD`
- Read passwords from env vars. If unset, fall back to the existing dev default `Qwenragadmin123!` and emit a warning log line so production never silently uses the dev password.
- Idempotency preserved: if a seeded email already exists in Supabase Auth, update `user_metadata.role` and password to match the desired state; otherwise create.
- Add the three new env-var entries to `repos/fast-api-backend/.env.example` with placeholder values and a comment explaining their purpose.
- Print a confirmation summary at the end (one line per seeded user with email + role + created-or-updated status).

### Out of scope
- A separate `npm run seed` proxy in the FE (Boss confirmed Python invocation only).
- Email invitation or password reset (not in this phase).
- Storing seeded user metadata anywhere outside Supabase Auth (no Postgres `seed_users` table).

## Acceptance Criteria
1. Running `python -m app.scripts.seed_admin` against a fresh Supabase project creates exactly three users with the three role values; rerunning is a no-op idempotently (updates if drift, otherwise unchanged).
2. With `SEED_SUPER_PASSWORD`, `SEED_ADMIN_PASSWORD`, `SEED_USER_PASSWORD` set in `.env`, all three seeded passwords match the env values.
3. With any of those env vars unset, the script logs a warning and uses the dev fallback for that user. No silent failure.
4. `.env.example` contains the three new entries with safe placeholder values (e.g. `SEED_SUPER_PASSWORD=change-me-in-real-env`) and a brief comment.
5. The script exits with code 0 on success, non-zero on any Supabase Admin API error.

## Implementation Notes

- **Files likely to touch:**
  - `repos/fast-api-backend/app/scripts/seed_admin.py` (extend the existing seed function from 1 user to 3; consider a small data-driven loop over a list of `{email, role, password_env}` dicts)
  - `repos/fast-api-backend/.env.example` (add the three env-var entries)
- **Patterns to follow:**
  - The script already uses the Supabase Admin client correctly — reuse its create/update branch logic.
  - Keep the dev fallback explicit (a constant at the top of the file) so it's discoverable.
- **Patterns to avoid:**
  - Do not commit real passwords to `.env.example`.
  - Do not silently substitute env vars without logging — ops must see what's happening.
- **Edge cases to handle:**
  - All three env vars set → no warning, all real passwords applied.
  - One env var set, two unset → warning for the unset ones; real password used where set.
  - All env vars unset (dev convenience) → warning that ALL three seeded users use the dev fallback; loud enough to notice but not fatal.
  - Supabase rate limit during create → let the existing retry/error path handle it (don't add new retry logic).
  - Email collision with a non-seeded user already in the project → existing update branch handles it; log a clear message that an out-of-band user got their metadata rewritten.
