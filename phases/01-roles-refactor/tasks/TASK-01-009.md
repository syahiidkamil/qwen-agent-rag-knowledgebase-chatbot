# TASK-01-009: Document rename end-to-end

## Type
feature

## Milestone
Milestone 4 — Knowledge base rename + closeout

## Goal
An admin can rename a knowledge-base document. The new filename appears immediately in the documents list and on source chips of future chat answers. The underlying storage object is not renamed.

## Context
The smallest user-facing addition in the phase. Today there's no way to fix a typo'd filename or rename a document for clarity short of delete-and-reupload (which loses chunks and incurs re-ingestion cost). This task lands the rename. The endpoint is admin-gated; the storage path stays immutable so existing chunks remain valid. This is functionally independent of M2/M3 — depends only on M1's role infra — so it could be done in parallel by a second person.

## Scope

### In scope
- Backend (`repos/fast-api-backend/app/api/documents.py`):
  - New endpoint `PATCH /api/documents/{id}` (admin+).
  - Request body: `{filename: str}`. Pydantic-validate: 1–255 chars after `.strip()`, no path separators (`/`, `\`), no NUL bytes.
  - Update `documents.filename` only; do NOT touch `storage_path` or any chunk-related field.
  - Return 200 with the updated document projection. 404 if document not found. 400 on validation error.
- Frontend (`repos/react-vite-frontend/src/features/admin/knowledge-base/`):
  - Add a ✏️ (rename) action icon to each row in the documents table (between the existing reingest and delete actions).
  - Click → opens a small Rename dialog (per `wireframes/admin-knowledge-base.md`).
  - Dialog has the filename pre-filled, Save / Cancel buttons.
  - On Save: optimistic UI update (row name changes immediately); on PATCH failure, revert the row + show toast.
  - Inline validation: empty filename disables Save with a small error message.

### Out of scope
- Renaming the underlying storage object (Supabase Storage doesn't support cheap rename; and chunks would have to be regenerated).
- Retroactively updating source chips on already-rendered chat turns (those came in the SSE payload at the time).
- A bulk rename UI.
- Filename history / audit.

## Acceptance Criteria
1. Signed in as admin, the documents table shows a ✏️ icon on each row alongside the existing reingest/delete icons.
2. Clicking ✏️ opens a dialog with the current filename pre-filled.
3. Saving with a new valid filename: the row's filename updates immediately (optimistic), the PATCH succeeds, the dialog closes.
4. Saving with an empty filename: Save is disabled until the user types something.
5. Saving with a filename containing a path separator: BE returns 400; FE shows inline error in the dialog.
6. After a successful rename, a chat answer that references that document shows the new filename in its source chip.
7. Deletion of the renamed document still cascades to chunks (regression — no change to the existing delete path).
8. The Supabase Storage object name is unchanged after rename (verifiable by downloading the file via the existing storage_path).
9. `PATCH /api/documents/{id}` with a user-role bearer returns 403; with no bearer returns 401.

## Implementation Notes

- **Files likely to touch:**
  - `repos/fast-api-backend/app/api/documents.py` (add PATCH handler)
  - `repos/fast-api-backend/app/schemas/document.py` (add `DocumentRenameIn`)
  - `repos/react-vite-frontend/src/features/admin/knowledge-base/DocumentsTable.tsx` (add rename action)
  - `repos/react-vite-frontend/src/features/admin/knowledge-base/RenameDialog.tsx` (new)
  - `repos/react-vite-frontend/src/services/DocumentService.ts` (add `rename(id, filename)` method)
- **Patterns to follow:**
  - Use the existing dialog primitives (shadcn `Dialog`).
  - React Hook Form + Zod for the rename input (`.claude/rules`).
  - Optimistic update pattern: update local store state immediately on Save click; rollback in the PATCH catch.
- **Patterns to avoid:**
  - Don't touch `storage_path` in the backend — it's an invariant for chunk integrity.
  - Don't re-run ingestion as part of rename — chunks are unchanged.
  - Don't add a confirm dialog ("are you sure?") — renames are reversible by renaming again.
- **Edge cases to handle:**
  - Document deleted between Open Dialog and Save → BE returns 404; FE shows toast "This file no longer exists" and refreshes the list.
  - Two admins rename the same document concurrently → last write wins (no optimistic locking this phase; documented acceptable).
  - User pastes a filename with leading/trailing whitespace → backend strips before save.
  - Filename = current filename → backend accepts as a no-op (idempotent).
