# TASK-01-004: Chat-mode toggle end-to-end

## Type
feature

## Milestone
Milestone 2 — User chat

## Goal
Super-admin can flip a "Public ↔ Internal" switch on the Landing config page; the value persists to Postgres. Admin (non-super) cannot reach this control on the FE or the endpoint on the BE.

## Context
The chat-mode setting is the lever that lets super-admin decide whether the public marketing landing page exposes the chat widget to anonymous visitors. This task lands the toggle as data + control surface; **gating the chat endpoint itself comes in TASK-01-005**, which depends on this task because it reads the field this task introduces. The data home is `landing_config.config` JSONB (no migration), per DECISIONS.md.

## Scope

### In scope
- Backend (`repos/fast-api-backend/app/api/landing_config.py`):
  - Update the existing `PUT /api/landing-config` to use `require_role("super_admin")` (admin alone must NOT pass).
  - Extend the `LandingConfigIn`/`LandingConfigOut` Pydantic schemas to recognize an optional `chat_mode: Literal["public", "internal"]` key inside the config blob.
  - Default `chat_mode` to `"public"` when the key is absent in stored config (defensive read for backwards-compat with existing rows).
  - Keep `GET /api/landing-config` publicly readable — the marketing landing page fetches it anonymously.
- Frontend (`repos/react-vite-frontend/src/features/landing-config/` or equivalent):
  - Add a "Chat mode" radio group at the top of the existing Landing config form: Public (default) / Internal.
  - Show "Currently: Public" or "Currently: Internal" chip near the radio, reflecting the *saved* state (dashed border when dirty + unsaved).
  - Reuse the existing single Save button — one save submits the whole config blob including chat_mode.
- Frontend route + sidebar:
  - Wrap the Landing config route with `RoleGuard(["super_admin"])`.
  - Show the "Landing config" sidebar entry only to super_admin (hide for admin).

### Out of scope
- Wiring chat-endpoint behavior to chat_mode — TASK-01-005.
- The public landing widget's "Sign in to chat" gate — TASK-01-005.
- Any other brand-preset field additions or changes.

## Acceptance Criteria
1. Signed in as super_admin, the Landing config page renders with the Chat mode radio at the top; brand-preset fields below remain functionally unchanged.
2. Switching the radio and clicking Save persists the value to `landing_config.config.chat_mode`; the "Currently: …" chip updates after save.
3. `PUT /api/landing-config` called with admin (non-super) bearer returns 403. The Landing config sidebar entry is hidden for admin.
4. `GET /api/landing-config` works without auth and returns `chat_mode` (defaulting to `"public"` if the key is absent).
5. Existing brand-preset save path still works — no regression in the rest of the Landing config form.
6. Direct browser navigation to the Landing config URL as admin redirects them away (RoleGuard).

## Implementation Notes

- **Files likely to touch:**
  - `repos/fast-api-backend/app/api/landing_config.py` (tighten gate; schema for chat_mode)
  - `repos/fast-api-backend/app/schemas/landing_config.py` if separate (add chat_mode Literal type)
  - `repos/react-vite-frontend/src/features/landing-config/*` (form + UI)
  - `repos/react-vite-frontend/src/routes/router.tsx` (RoleGuard wrap)
  - Sidebar / admin shell component (conditional render)
- **Patterns to follow:**
  - JSONB stays free-form on the DB side; the Pydantic schema is the only place we encode the chat_mode contract.
  - Use `require_role` from TASK-01-001 — don't reimplement the role check.
- **Patterns to avoid:**
  - Don't add a new DB column for chat_mode — DECISIONS.md locked it inside the JSONB blob.
  - Don't put the chat_mode toggle on its own page — Boss chose to bundle into Landing config.
  - Don't save chat_mode through a separate endpoint; one Save covers the whole blob (existing UX).
- **Edge cases to handle:**
  - `landing_config` row missing entirely (fresh install) → GET still returns sensible defaults (`{config: {chat_mode: "public", ...}}`).
  - `chat_mode` set to an invalid string by direct DB tampering → Pydantic rejects on read; FE falls back to "public".
  - Save in flight when super-admin clicks Save again → existing form-submit guard (disabled button while pending) handles it.
