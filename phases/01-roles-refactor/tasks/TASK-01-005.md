# TASK-01-005: Internal-mode chat gating end-to-end

## Type
feature

## Milestone
Milestone 2 — User chat

## Goal
When chat_mode is `"internal"` AND the visitor is not signed in, both the chat endpoint and the public landing widget block the chat. Logged-in users (any role) always chat normally. When chat_mode is `"public"`, behavior is unchanged from today.

## Context
This is the gate that delivers the client's primary requirement — making the chat widget internal-only. The chat_mode field already exists (TASK-01-004); this task makes it *do something*. Backend enforcement is authoritative (returns 401); FE check is purely UX. This task is also the regression net for the public-mode case: TC-01-011 must keep passing.

## Scope

### In scope
- Backend (`repos/fast-api-backend/app/api/chat.py`):
  - Add `get_current_user_optional` (from TASK-01-001) as a dependency.
  - At the top of the chat handler, read `landing_config.config.chat_mode` (default `"public"` if absent).
  - If `chat_mode == "internal"` AND no `AuthUser` present → return 401 with `{"error": {"code": "INTERNAL_MODE_REQUIRES_AUTH", "message": "Sign in to chat."}}`.
  - Otherwise proceed with the existing chat flow.
- Frontend (`repos/react-vite-frontend/src/features/chat/` or the marketing landing chat widget):
  - On mount, fetch `landing_config` (already done if it's used for brand presets — reuse the existing fetch).
  - If `chat_mode === "internal"` AND `!isAuthenticated` → render the "Sign in to chat" gate UI in place of the chat form (see `wireframes/public-landing-widget.md` State B). The gate has a `[Sign in]` button linking to `/login`.
  - If `chat_mode === "internal"` AND `isAuthenticated` → render the normal chat widget (any role passes).
  - If `chat_mode === "public"` → render the normal chat widget (current behavior).
- Mid-conversation flip behavior (passive — per DECISIONS.md): if the visitor was chatting anonymously and the next POST returns 401, the widget switches to the gate UI; prior conversation history stays visible but greyed.

### Out of scope
- The `/workspace` route's chat widget — that's TASK-01-006.
- Any active termination of in-flight SSE streams when mode flips — explicitly out of scope per DECISIONS.md (passive flip).
- Chat behavior when authenticated user's token expires mid-stream — existing behavior.

## Acceptance Criteria
1. With chat_mode = `"public"`: anonymous visitor on the landing page sees the chat widget and can chat (TC-01-011 passes).
2. With chat_mode = `"internal"` AND no auth: anonymous visitor sees the "Sign in to chat" gate; the chat input is not rendered; the `[Sign in]` button navigates to `/login`.
3. With chat_mode = `"internal"` AND signed in as any role (super_admin / admin / user): visitor sees the chat widget normally and can chat.
4. Direct `POST /api/chat` with no Authorization header when chat_mode is `"internal"` returns 401 with the structured error body.
5. Direct `POST /api/chat` with a valid Bearer when chat_mode is `"internal"` returns 200 and the SSE stream (existing behavior).
6. Mid-conversation flip (anonymous user mid-chat, super-admin flips to internal): user's NEXT message attempt receives 401; widget switches to the gate UI; prior turns stay visible but greyed.
7. Mid-conversation flip back to `"public"`: anonymous user refreshes and chat widget returns to normal.

## Implementation Notes

- **Files likely to touch:**
  - `repos/fast-api-backend/app/api/chat.py` (add optional auth + chat_mode read + 401 branch)
  - `repos/fast-api-backend/app/services/chat.py` (probably no change — the gate happens before stream_answer is called)
  - `repos/react-vite-frontend/src/features/chat/ChatWidget.tsx` (or equivalent — the marketing chat widget component)
  - Possibly a small `useLandingConfig` hook if not already present (fetch + cache)
- **Patterns to follow:**
  - Reuse the existing `landing_config` fetch on FE — don't add a second fetch just for chat_mode.
  - 401 error body convention matches `documents.py` and the new auth errors from TASK-01-001.
  - FE auth state from `useAuthStore.isAuthenticated`.
- **Patterns to avoid:**
  - Don't trust the FE for the gate — BE must enforce. FE is for UX only.
  - Don't query the chat_mode on every chat request from the FE — cache it (component-level state or a hook with a short TTL is fine).
  - Don't add a "are you sure" confirm dialog to the mid-flip case — passive flip per DECISIONS.md.
- **Edge cases to handle:**
  - `landing_config` row missing → both BE and FE treat as `"public"` (full backwards-compat).
  - Network flake while fetching `landing_config` on the FE → fail-open to showing the chat widget (UX > strict gating; BE still enforces the gate authoritatively).
  - User logs in via a new tab; the marketing widget tab doesn't auto-refresh auth → next chat send still works because the BE accepts the token; FE state will catch up on next navigation.
