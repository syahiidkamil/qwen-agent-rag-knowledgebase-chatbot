# TASK-01-007: Users CRUD backend

## Type
feature

## Milestone
Milestone 3 — Admin user management

## Goal
Admin and super_admin can list users, create users (with email + password + role), deactivate users, and reactivate users — all via REST endpoints that wrap Supabase Auth's admin API.

## Context
The phase needs to be self-serve for the client: admins should onboard their CS / sales team without re-running the seed script or touching the Supabase dashboard. This task ships the backend half; TASK-01-008 ships the UI on top. Deactivation maps to Supabase's `banned_until` per DECISIONS.md (cheapest, built-in enforcement). All four endpoints share the same auth gate (`require_role("admin")` — both admin and super_admin pass).

## Scope

### In scope
- New file or extension: `repos/fast-api-backend/app/api/users.py` (mount at `/api/users`):
  - `GET /api/users` (admin+): list all users from Supabase Auth Admin API; project to `{id, email, role, status: "active"|"deactivated", created_at}`. Status derived from `banned_until`: `null` → active; any future date → deactivated.
  - `POST /api/users` (admin+) with body `{email, password, role}`: validate role is one of `super_admin`/`admin`/`user`; validate password length >= 8; create via Supabase Admin API with `user_metadata: {role}`; return new user projection. 409 on email collision (Supabase returns this; surface verbatim).
  - `PATCH /api/users/{id}/deactivate` (admin+): set `banned_until` to a far-future date (e.g. 100 years from now). Reject self-deactivation server-side as defense-in-depth: if `caller.id == id`, return 400 with `{"error": {"code": "SELF_DEACTIVATE_FORBIDDEN", "message": "..."}}`.
  - `PATCH /api/users/{id}/reactivate` (admin+): set `banned_until` to `null`.
- Wire the router in `repos/fast-api-backend/app/main.py` if a new file.
- Use the existing `supabase` admin client from `app/core/supabase.py` (uses `SUPABASE_SECRET_KEY`).

### Out of scope
- UI for any of this — TASK-01-008.
- Password reset, email invitations, magic links — explicitly out of scope for the whole phase.
- Role editing of an existing user (admin must deactivate + recreate per DECISIONS.md).
- Audit log of who did what — out of scope.
- Rate limiting — defer; Supabase Admin API has its own limits.

## Acceptance Criteria
1. `GET /api/users` with admin or super_admin bearer returns the user list with the four projection fields. Called with user bearer returns 403. Called with no auth returns 401.
2. `POST /api/users` with `{email, password: "longenough", role: "user"}` creates a Supabase Auth user with `user_metadata.role = "user"`; the new user can sign in immediately afterward.
3. `POST /api/users` with a password shorter than 8 chars returns 400 with structured error. With a role not in the known set, returns 400. With an email that already exists in Supabase, returns 409.
4. `PATCH /api/users/{id}/deactivate` flips the user to deactivated; subsequent sign-in attempts by that user fail with a banned-account error.
5. `PATCH /api/users/{id}/reactivate` restores the user; they can sign in again.
6. Calling deactivate on the caller's own id returns 400 with `SELF_DEACTIVATE_FORBIDDEN`, regardless of role.
7. All four endpoints require `require_role("admin")` — admin AND super_admin pass; user does not.

## Implementation Notes

- **Files likely to touch:**
  - `repos/fast-api-backend/app/api/users.py` (new)
  - `repos/fast-api-backend/app/schemas/user.py` (new — Pydantic request/response models)
  - `repos/fast-api-backend/app/main.py` (include the new router)
  - Possibly `repos/fast-api-backend/app/core/supabase.py` if the existing admin client needs a thin convenience wrapper for user ops.
- **Patterns to follow:**
  - Match the API conventions in `documents.py` and `landing_config.py` — structured error bodies, RESTful URLs (kebab-case if multi-word, but here single nouns).
  - Use Pydantic `Literal["super_admin", "admin", "user"]` for the role field — schema-level validation, no manual check needed.
  - Use the existing `require_role` factory from TASK-01-001.
- **Patterns to avoid:**
  - Don't write directly to a Postgres `users` table — there is none. The source of truth is Supabase Auth.
  - Don't reimplement password hashing — Supabase handles it.
  - Don't expose Supabase-internal fields (`encrypted_password`, raw `user_metadata`, etc.) in the API response — project to the four documented fields only.
  - Don't add pagination this phase — list is expected to be small (<50 users).
- **Edge cases to handle:**
  - Caller's JWT is valid but the user no longer exists in Supabase (race after concurrent deactivation) → 403 surfaces naturally from auth deps; document the noisy log line.
  - Concurrent deactivate by two admins on the same target → both succeed; idempotent.
  - Deactivate on a non-existent user id → 404.
  - Reactivate on an already-active user → 200, idempotent.
  - Supabase Admin API down → 502 to the caller with a clear message.
