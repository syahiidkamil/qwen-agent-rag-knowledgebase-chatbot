# TASK-01-001: Backend role-aware auth dependencies

## Type
refactor

## Milestone
Milestone 1 — Close security hole + role infrastructure

## Goal
The backend stops treating "authenticated" as "admin." Every privileged endpoint authorizes based on `user_metadata.role`, and the existing security hole (any signed-in Supabase user is currently admin-equivalent) is closed.

## Context
This is the load-bearing first task of the whole phase. Today, `get_current_admin` in `app/core/auth.py` verifies a Supabase JWT and returns an `AuthUser` for ANY signed-in user — it never inspects `user_metadata.role`. The seed script writes `{"role": "admin"}` into that field, but the backend ignores it. Until this task ships, **every other task that creates a non-admin user (002, 003, 006, 007, 008) would immediately grant those users full admin access**. This task ships nothing user-visible on its own, but unblocks everything else and removes a real production risk.

## Scope

### In scope
- Modify `app/core/auth.py` so the existing `get_current_admin` dependency now enforces `user_metadata.role in ("admin", "super_admin")`, returning 403 otherwise (not 401 — they're authenticated, just not authorized).
- Add `require_role(*allowed_roles)` factory dependency in `app/core/auth.py` that returns a callable suitable for `Depends(...)`. Used by every role-gated endpoint going forward (super_admin landing config, admin user CRUD, etc.).
- Add `get_current_user_optional` dependency that verifies the bearer token if present and returns `AuthUser | None` (no exception if missing). Used by the chat endpoint in TASK-01-005 to gate on chat_mode + auth presence together.
- Update existing usages of `get_current_admin` in `app/api/documents.py` and `app/api/landing_config.py` to call the new role-enforcing version (no signature change). Verify all routes still attach the dependency.
- Structured 403 error body matches the existing API convention (`{"error": {"code": "FORBIDDEN", "message": "..."}}`).

### Out of scope
- Any new endpoints (those land in 004, 005, 007, 009).
- Frontend role handling — that's TASK-01-003.
- Seed script changes — TASK-01-002.
- Per-role granular policies (super_admin-only routes get `require_role("super_admin")` directly in their owning task).

## Acceptance Criteria
1. Calling any existing admin endpoint with a valid Supabase JWT whose `user_metadata.role` is missing, `"user"`, or any unknown value returns HTTP 403 with the structured error body.
2. Calling the same endpoints with a JWT whose role is `"admin"` or `"super_admin"` succeeds as before.
3. `require_role("admin")` and `require_role("super_admin")` are importable from `app.core.auth` and behave as documented: 403 on missing/wrong role, pass-through on match. `require_role("admin")` accepts both `admin` and `super_admin` (admins are a subset of super-admins' privileges).
4. `get_current_user_optional` returns `None` for unauthenticated requests, the verified `AuthUser` for valid tokens, and raises 401 only for tokens that are *present but invalid* (malformed, expired, wrong signature).
5. The existing `documents` and `landing_config` endpoints continue to work for the seeded admin user (no regression in TC-01-011, TC-01-012 paths once seed is also updated).
6. No frontend changes required for this task to merge — the existing FE keeps working because seeded admin still has `role: "admin"`.

## Implementation Notes

- **Files likely to touch:**
  - `repos/fast-api-backend/app/core/auth.py` (primary — rewrite the dependency function)
  - `repos/fast-api-backend/app/api/documents.py` (verify Depends still wires correctly)
  - `repos/fast-api-backend/app/api/landing_config.py` (same)
- **Patterns to follow:**
  - Match the existing FastAPI `Depends` style; do not introduce a class-based dependency unless needed.
  - Re-use the existing JWT verification path (ES256 via JWKS, HS256 fallback) — only the post-verification authorization step changes.
  - Error shape: `HTTPException(status_code=403, detail={"error": {"code": "FORBIDDEN", "message": "..."}})` matching `documents.py`'s existing error patterns.
- **Patterns to avoid:**
  - Don't read `user_metadata.role` ad-hoc in route handlers — always go through `require_role(...)` so the policy lives in one place.
  - Don't conflate 401 (no/bad token) with 403 (good token, wrong role). They mean different things to the FE.
- **Edge cases to handle:**
  - `user_metadata` field entirely absent → 403 with "missing role" message.
  - `role` field present but value not in the known set → 403; log the unknown value at INFO for ops visibility.
  - Empty Authorization header on a `get_current_user_optional` endpoint → return None silently.
  - Malformed Authorization header (e.g. "Bearer" with no token) → 401, not None.
