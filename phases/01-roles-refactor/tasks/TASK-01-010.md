# TASK-01-010: Phase closeout — docs + full TC sweep

## Type
docs

## Milestone
Milestone 4 — Knowledge base rename + closeout

## Goal
The phase is documented in the system-design folder, every test case is executed end-to-end one final time, and the run result is recorded. After this task, the phase can be declared done.

## Context
Closeout exists to catch regressions in features we didn't directly modify (cascade delete on document delete, public chat in chat_mode=public, KB upload), and to leave the project's living docs in sync with what shipped. The 12 test cases were designed as the acceptance suite for the phase; running them all in one sitting at the end gives a clean signal. No new code in this task — it's documentation + verification.

## Scope

### In scope
- Update `docs/system-design/README.md`:
  - In the "Components" section, mention that admin auth now enforces `user_metadata.role` (`super_admin` / `admin` / `user`).
  - In the "Data model snapshot" section, add the `chat_mode` key on `landing_config.config` and note its default (`"public"`).
  - In the "Environment matrix", add `SEED_SUPER_PASSWORD`, `SEED_ADMIN_PASSWORD`, `SEED_USER_PASSWORD` rows.
- Run the full 12-test sweep via `/qa-manual-test-run` against the running BE + FE.
- Record the run result in `phases/01-roles-refactor/test-runs/<YYYY-MM-DD>-closeout.md` with each TC's pass/fail status and any deviation notes.
- If any TC fails: file a follow-up task or fix-in-place; do not mark the phase done until all 12 pass.

### Out of scope
- New code or refactors. If a regression is discovered, the fix is a separate task (or amends an existing one) — closeout's job is to surface, not silently patch.
- Updating other docs (`chat-pipeline.md`, `ingestion-pipeline.md`, `rag-overview.md`) — they don't materially change in this phase.

## Acceptance Criteria
1. `docs/system-design/README.md` accurately reflects the role enforcement, the `chat_mode` field, and the new env vars.
2. All 12 test cases (TC-01-001 through TC-01-012) have been executed against the deployed (or locally-running) build and recorded.
3. The test-run record lives at `phases/01-roles-refactor/test-runs/<YYYY-MM-DD>-closeout.md` with per-TC status (pass/fail/blocked) and any free-form notes from the qa-manual-tester sub-agent.
4. All 12 TCs are pass status, OR every failure has a linked follow-up task tracking the fix.
5. The phase's `tasks/README.md` checkboxes are all checked.

## Implementation Notes

- **Files likely to touch:**
  - `docs/system-design/README.md`
  - `phases/01-roles-refactor/test-runs/<YYYY-MM-DD>-closeout.md` (new)

- **Patterns to follow:**
  - Match the existing `docs/system-design/README.md` tone and table format.
  - Test-run record format: a small markdown file with a one-row-per-TC table (TC id, title, status, notes).
- **Patterns to avoid:**
  - Don't rewrite the existing system-design docs — minimal-touch updates only.
  - Don't silently patch failing TCs without filing a follow-up.
- **Edge cases to handle:**
  - A TC is blocked because some other deployment issue (env var missing in Railway, etc.) — record as "blocked" with the blocker; not a failure of this phase per se.
  - A TC's expected behavior turned out to be subtly wrong post-implementation — update the TC to match reality AND note the change in the run record.
