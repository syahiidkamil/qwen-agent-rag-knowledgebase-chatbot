# TASK-01-003: Frontend role-aware auth store + RoleGuard + login redirect

## Type
feature

## Milestone
Milestone 1 — Close security hole + role infrastructure

## Goal
The frontend knows the signed-in user's role and routes them based on it: super_admin/admin → `/admin`, user → `/workspace`, unknown role → signed out with a clear error.

## Context
Today `useAuthStore` exposes only `isAuthenticated` and `email` — no role. `ProtectedRoute` gates only on "authenticated." This task adds the role layer: extract role from the Supabase session, expose it through the store, add a `RoleGuard` for role-restricted routes, and make `/login` redirect by role. Without this, the seeded `user` from TASK-01-002 can sign in but has no destination — TASK-01-006 will add `/workspace`, but the redirect logic must exist first so users land there automatically.

## Scope

### In scope
- Extend `repos/react-vite-frontend/src/stores/useAuthStore.ts`:
  - Add `role: "super_admin" | "admin" | "user" | null` field.
  - In `applySession` (or equivalent), read `session.user.user_metadata.role` and store it. Treat missing/unknown as `null`.
- Add `repos/react-vite-frontend/src/routes/RoleGuard.tsx` (or fold into `ProtectedRoute.tsx` — implementer's call):
  - Wrapper that accepts `allowedRoles: string[]`, checks `useAuthStore`'s role, and redirects unauthorized users to their default destination (admin/super_admin → `/admin`, user → `/workspace`).
  - If `role === null`, sign out and redirect to `/login` with the "Account misconfigured" message in URL state.
- Update `repos/react-vite-frontend/src/features/auth/Login.tsx` (or wherever the login page lives):
  - On successful sign-in, read role from the store and redirect:
    - `super_admin` or `admin` → `/admin`
    - `user` → `/workspace` (route exists in TASK-01-006; for now navigation works even if the route 404s)
    - `null` → sign out + show inline "Account misconfigured" error.
- Update `repos/react-vite-frontend/src/routes/router.tsx` to apply `RoleGuard` on admin routes (so a logged-in `user` can't reach `/admin/*`).

### Out of scope
- Building the `/workspace` route itself — that's TASK-01-006.
- New sidebar items (Users page lands in 008; Landing config in 004).
- Per-page role-aware UI inside admin views (sidebar visibility difference between admin and super_admin is in 004 and 008).

## Acceptance Criteria
1. After signing in as seeded super_admin or admin, the browser lands on `/admin` (or wherever the existing admin landing is) and shows the existing admin shell.
2. After signing in as seeded user, the browser navigates to `/workspace`. The route may render a 404 placeholder until TASK-01-006 ships — that's expected.
3. After signing in with an account whose JWT has no `user_metadata.role`, the FE signs them out and shows the inline error "This account needs setup. Contact your administrator."
4. A signed-in `user` who manually types `/admin` in the address bar is redirected away from admin routes (to `/workspace`).
5. `useAuthStore.role` is readable from any component and is correctly typed.
6. No regression: existing seeded admin continues to access existing admin pages exactly as before.

## Implementation Notes

- **Files likely to touch:**
  - `repos/react-vite-frontend/src/stores/useAuthStore.ts`
  - `repos/react-vite-frontend/src/routes/ProtectedRoute.tsx` (extend) OR new `RoleGuard.tsx`
  - `repos/react-vite-frontend/src/features/auth/Login.tsx` (post-success redirect)
  - `repos/react-vite-frontend/src/routes/router.tsx` (wire RoleGuard)
- **Patterns to follow:**
  - Use Zustand idioms already in `useAuthStore` (no separate context provider).
  - Use React Router v7's `Navigate` for redirects, matching existing `ProtectedRoute` pattern.
  - Keep role check pure-functional (a small `canAccess(role, allowedRoles)` helper) so it's trivially testable.
- **Patterns to avoid:**
  - Don't sprinkle `if (role === "admin")` checks in components; use `RoleGuard` at the route level and let components assume access is correct once mounted.
  - Don't store the raw Supabase session in Zustand — keep deriving the minimal fields (email, role, isAuthenticated) the way the existing store does.
- **Edge cases to handle:**
  - Page refresh while logged in: `applySession` re-runs from the persisted session; role must repopulate without an extra round-trip.
  - Sign-out clears `role` back to `null`.
  - Role missing → sign out + redirect path includes the misconfigured-error flag so the login page can render the message.
  - A user with role `admin` should pass `RoleGuard(["admin", "super_admin"])` (admin is a subset of super_admin's powers for shared surfaces like Users).
