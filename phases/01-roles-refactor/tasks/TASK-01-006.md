# TASK-01-006: User workspace + read-only KB access

## Type
feature

## Milestone
Milestone 2 — User chat

## Goal
A signed-in `user` lands on `/workspace`, sees a read-only list of knowledge-base files, and can chat with Aira via an auto-opened wider chat panel that's minimizable to a bubble.

## Context
This is the user-facing payoff of the role refactor: CS reps, sales, support — any internal teammate — gets a workspace they can actually use. The chat panel is the same component as the marketing widget, rendered larger and auto-opened. The read-only KB list is what they can ask Aira *about*. This task touches BE (relax read auth) + FE (new route + layout); it's a vertical slice.

## Scope

### In scope
- Backend (`repos/fast-api-backend/app/api/documents.py`):
  - Change `GET /api/documents` to require any authenticated role (super_admin / admin / user) rather than `require_role("admin")`. Use a new dependency `get_current_authenticated` (any role) — or directly use the FastAPI standard pattern of `Depends(get_current_user)` if that's the existing shape after TASK-01-001.
  - Write/delete/reingest endpoints (`POST`, `DELETE`, `POST /{id}/reingest`, and the new rename from TASK-01-009) stay `require_role("admin")` — no change.
  - Response shape unchanged; FE just hides admin-only columns.
- Frontend:
  - New route `/workspace` (or per `router.tsx` convention) wrapped with `RoleGuard(["super_admin", "admin", "user"])` — any logged-in role can view their own workspace.
  - Two-column layout per `wireframes/user-workspace.md`:
    - Left: read-only KB list (filename, updated_at). No upload, rename, delete, or reingest controls.
    - Right: chat widget component (reuse existing), but rendered larger (~420 px wide) and auto-opened on mount.
  - Minimize button (chevron in the chat header) collapses the chat to a floating bubble; clicking the bubble re-expands. Preference persisted in localStorage (`workspace_chat_open=true|false`); default `true`.
  - Top bar with the user's email + a sign-out menu (reuse existing UI primitives).

### Out of scope
- Document preview / row click handler (note in code: future-friendly, do not implement).
- Search or filter on the KB list (small list expected; defer).
- Per-document permissions (all logged-in users see all KB files).
- Any admin sidebar appearing in `/workspace` — this is a different shell than `/admin`.

## Acceptance Criteria
1. Signed in as seeded user, navigating to `/workspace` (or being redirected there from `/login`) shows the two-column layout with the KB list on the left and chat panel on the right, auto-opened.
2. The KB list shows the same documents an admin sees, but only the filename and updated date — no chunk count, no status, no error message, no actions.
3. The user can send a chat message and receive a streamed answer (TC-01-002 happy path).
4. Clicking the chat header's minimize chevron collapses the panel to a floating bubble; clicking the bubble re-expands. Preference persists across page reloads.
5. A signed-in admin or super_admin can also reach `/workspace` if they navigate there directly (RoleGuard allows all logged-in roles); their default landing after sign-in is still `/admin` per TASK-01-003.
6. `GET /api/documents` called with a user JWT returns 200; called with no auth returns 401; called with an admin JWT continues to work for the admin pages.
7. Anonymous visitor typing `/workspace` is bounced to `/login`.

## Implementation Notes

- **Files likely to touch:**
  - `repos/fast-api-backend/app/api/documents.py` (relax GET, leave others alone)
  - `repos/react-vite-frontend/src/features/workspace/Workspace.tsx` (new)
  - `repos/react-vite-frontend/src/features/workspace/DocumentList.tsx` (new — read-only variant)
  - `repos/react-vite-frontend/src/routes/router.tsx` (new route + RoleGuard)
  - Existing chat widget component — reuse, do not fork; if size/layout customization is needed, pass props rather than copy-paste.
- **Patterns to follow:**
  - Use the existing documents-fetching hook/service if one exists; the FE shouldn't have two ways to fetch the same data.
  - Follow the existing shell pattern for top-bar + main content; no new app-shell abstraction.
  - localStorage key namespaced: `aira:workspace_chat_open`.
- **Patterns to avoid:**
  - Don't build a second chat widget component for workspace — reuse, parameterize via props (e.g. `width`, `defaultOpen`).
  - Don't fetch landing_config in the workspace — chat_mode doesn't matter for logged-in users (TASK-01-005 covers this; chat works for any authenticated role regardless of mode).
  - Don't add an admin-style sidebar to workspace.
- **Edge cases to handle:**
  - Empty KB list → friendly empty-state: "No documents yet — your admin is still curating the corpus." Chat still works.
  - localStorage write fails (private browsing modes) → fall through silently, default to open.
  - Chat panel minimized AND user navigates away then back → restored from localStorage on re-mount.
  - User's JWT expires while on /workspace → next chat send returns 401; auth store catches it; user bounced to /login (existing flow).
