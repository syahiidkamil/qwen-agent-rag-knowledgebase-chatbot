# TASK-01-008: Users management page

## Type
feature

## Milestone
Milestone 3 — Admin user management

## Goal
Admin and super_admin see a `/admin/users` page where they can list every account, create new users (email + password + role), and deactivate / reactivate accounts. After creating, the password is shown once with a copy affordance because there is no email invitation.

## Context
This is the UI that makes the backend from TASK-01-007 usable by the client's team. Without this, the client has to ask their dev to re-run the seed script every time they need to onboard someone. The page also enforces the "super-admin cannot deactivate self" rule at the UI (the row's button is simply absent). The defense-in-depth backend check from TASK-01-007 catches anyone who tries to bypass.

## Scope

### In scope
- New route `/admin/users` wrapped in `RoleGuard(["super_admin", "admin"])`. Add to `router.tsx` and to the admin sidebar (visible to both roles).
- Page layout per `wireframes/users.md`:
  - Table with columns: Email, Role, Status, Actions.
  - "+ Add user" button top-right.
  - On each row: Deactivate button for active users; Reactivate for deactivated. The super_admin's own row hides the action column entry (or shows "—").
- Add user dialog:
  - Email input.
  - Password input with reveal (👁) and copy (📋) icons.
  - Role radio: user / admin / super_admin (default user).
  - On Create: `POST /api/users`; on success, dialog swaps to the post-create confirmation; on 4xx (409 email collision, 400 validation) inline error.
- Post-create confirmation:
  - Shows the password again with a copy icon and the warning "Share these credentials now — this is your only chance to copy the password."
  - Single [Done] button closes the dialog and wipes the password from memory.
- Deactivate / Reactivate row actions:
  - Click → `PATCH /api/users/{id}/deactivate` (or `/reactivate`); no confirm dialog (reversible).
  - Row status flips immediately on success.

### Out of scope
- Search, filter, pagination — small list expected.
- Bulk operations — single-row actions only.
- Role editing of existing users — out of scope per DECISIONS.md.
- Audit / activity log on user actions — out of scope.

## Acceptance Criteria
1. Signed in as admin or super_admin, the Users sidebar entry is visible and `/admin/users` renders the list of all users with correct projection fields.
2. Signed in as user, the Users sidebar entry is hidden and direct navigation to `/admin/users` redirects to `/workspace`.
3. Add user dialog: filling all fields and clicking Create issues `POST /api/users`; on success, the dialog swaps to the post-create confirmation showing the password + copy button.
4. After Done is clicked on the confirmation, the password is no longer accessible in the UI (DOM-wiped; not just hidden).
5. Server-side validation errors (password too short, email already exists) surface as inline errors in the Add dialog without dismissing it.
6. Deactivate button on an active row flips it to deactivated status with no confirm dialog; button label becomes Reactivate.
7. Reactivate button does the inverse.
8. The signed-in super_admin's own row shows no Deactivate (or Reactivate) button.
9. The just-created user can sign in immediately at `/login` and lands on the correct surface per their role.

## Implementation Notes

- **Files likely to touch:**
  - `repos/react-vite-frontend/src/features/users/UsersPage.tsx` (new)
  - `repos/react-vite-frontend/src/features/users/AddUserDialog.tsx` (new)
  - `repos/react-vite-frontend/src/features/users/PostCreateConfirmation.tsx` (new — or inline inside the dialog)
  - `repos/react-vite-frontend/src/services/UserService.ts` (new — wraps the 4 endpoints)
  - `repos/react-vite-frontend/src/routes/router.tsx` (route + RoleGuard)
  - Admin sidebar / shell (add Users nav item)
- **Patterns to follow:**
  - Match the existing admin pages' table style and dialog primitives (likely shadcn/ui components per `.claude/rules/frontend-react-vite-tailwind-4-and-shadcn.md`).
  - Use React Hook Form + Zod for the Add user form (`.claude/rules` confirms the project convention).
  - Service class pattern (`UserService`) matches `.claude/rules` recommendation.
- **Patterns to avoid:**
  - Don't render the post-create password in plain text in the DOM for any longer than needed — wipe on Done click.
  - Don't allow the dialog to be dismissed while the post-create confirmation is showing (force the user to acknowledge they've copied the password).
  - Don't auto-copy the password to clipboard on dialog open — explicit click via the copy icon (user agency).
  - Don't show Deactivate confirm dialogs — DECISIONS.md and wireframes both say no.
- **Edge cases to handle:**
  - Loading list: skeleton rows.
  - Empty list: should never happen post-seed, but render "No users yet."
  - Concurrent deactivate by another admin → on the next list refresh, status updates; no special handling needed.
  - Network failure on create → keep the dialog open, show toast or inline error.
  - Reactivating a user who was deactivated long ago → just clears `banned_until`; no other state to repair.
  - Self-row hiding: detect via `useAuthStore.user.id === row.id`; do not rely on email comparison (immutable user id is safer).
